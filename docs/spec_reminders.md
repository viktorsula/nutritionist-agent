# Спецификация: Напоминания клиенту + контроль ответа

Статус: согласовано с владельцем 3 июля 2026. Реализуется двумя фазами.
Клиенту сообщения называются **«Напоминания»**; нутрициолог управляет ими в блоке
кабинета **«Задачи и заметки»**.

## Идея

Нутрициолог заводит список напоминаний клиенту с временем и регулярностью. Ассистент
шлёт их в Telegram по расписанию (в часовом поясе клиента). Часть напоминаний просто
уведомительные, часть **ждут ответа** (вес, замеры, анализы, сон) — ассистент это
контролирует: нет ответа → повтор; ответ пришёл → срабатывание закрыто и данные внесены
в карточку клиента.

Примеры:
- «Выпить стакан воды утром» — 07:00, ежедневно, уведомительное.
- «Поделитесь сегодняшним весом» — 07:00, ежедневно, **ждём ответ (вес)**.
- «Сделайте замеры талии и шеи и сообщите» — 18:00, понедельник, **ждём ответ (замеры)**.

## Ключевые решения (зафиксированы)

1. **Модель В** — отдельные таблицы `reminders` (шаблон) + `reminder_occurrences`
   (срабатывания). Напоминание ≠ разовая `tasks`-задача: у ежедневного шаблона нет
   терминального статуса, «закрывается» его сегодняшнее срабатывание.
2. **Пакетная отправка**: все напоминания клиента на одно и то же локальное время идут
   **одним сообщением**. Уведомительные и «ждущие ответа» смешиваются в одном пакете.
3. **Детект ответа — по типу** (вариант «а»): у напоминания есть ожидаемый показатель;
   срабатывание закрывает событие нужного типа, залогированное после отправки.
4. **Кадэнс догона — из профиля по типу ожидаемого ответа** (дефолты в `system_settings`,
   переопределяемы на напоминании). Единая формула срока:
   > `срок_сдаться = min(отправлено + окно_из_профиля, следующее_плановое_срабатывание)`
   Повтор каждые `повтор_через`, до `макс_повторов`, но не позже `срок_сдаться`.
   Клип по «следующему срабатыванию» реально бьёт только по ежедневным (догон внутри дня);
   для еженедельных/разовых многодневный догон применяется полностью.

   | Ожидаемый ответ | Событие-закрытие | Повтор через | Макс | Сдаться |
   |---|---|---|---|---|
   | Вес | measurements.weight | 3 ч | 1 | конец дня |
   | Замеры (талия/шея/бёдра) | measurements.* | 1 день | 2 | 3 дня |
   | Анализы | lab_results | 3 дня | 1 | 7 дней |
   | Сон | client_metrics (sleep) | 3 ч | 1 | конец дня |
   | Подтверждение/текст | любой ответ клиента | 3 ч | 1 | конец дня |
   | Уведомление (none) | — | — | — | ответа не ждём |

5. **«Сдались»** (ответа так и нет) → событие low-severity в панель «Алерты» (без спама
   в Telegram нутрициологу).
6. **Единая модель «контролируемый показатель»** (обобщение замеров/сна/произвольных
   данных, по образцу `tracked_lab_indicators`):
   - Каталог `client_profiles.controlled_metrics` (JSONB): `[{key,label_ru,label_en,unit,category}]`.
     Нутрициолог добавляет любой индивидуальный показатель клиента («утренний пульс»,
     «часы сна», «уровень стресса 1–10»).
   - Категории → хранилище: `physical` (weight/waist/neck/hips) → `measurements` (колонки
     уже есть); `lab` → `lab_results`; `sleep` → `client_metrics` (bedtime/wake/duration);
     `custom` → `client_metrics(client_id, metric_key, value, unit, measured_at)` (long-формат).
   - Обобщённый инструмент оркестратора `log_measurement(metric_key, value)` роутит по
     категории. Вес/замеры/сон — частные случаи.
   - «Ожидаемый ответ» напоминания = ключ показателя из каталога **или** «текст» **или** «none».

## Фаза 1 — напоминания (без контроля ответа)

Пункты 1–3 (проактивная рассылка). Таблицы `reminders` + `reminder_occurrences`
(occurrences уже создаём — нужны для дедупа отправки и как основа Фазы 2).

- **Миграция `013_reminders.sql`:**
  - `reminders(id, client_id FK, title, remind_at TIME, recurrence
    once|daily|weekly, weekday SMALLINT NULL, remind_date DATE NULL /*для once*/,
    requires_response BOOL DEFAULT false /*используется в Ф2*/, active BOOL DEFAULT true,
    created_by, created_at, updated_at)`.
  - `reminder_occurrences(id, reminder_id FK, client_id, due_date DATE, sent_at,
    UNIQUE(reminder_id, due_date))` — дедуп «одно срабатывание в день». Ф2 добавит
    `status/response_event_id/followups_sent/next_followup_at`.
- **queries:** `create_reminder / update_reminder / delete_reminder /
  list_reminders(client_id) / list_active_reminders() (join clients: telegram_id,
  timezone) / occurrence_exists(reminder_id, due_date) / record_occurrence(...)`.
- **Планировщик** `api/scheduler.py::run_reminders()` в `run_scheduler_pass()`:
  для каждого клиента — локальное now; собрать напоминания, у которых `remind_at` совпал
  с текущей минутой И recurrence-сегодня (daily: всегда; weekly: weekday совпал; once:
  remind_date == сегодня) И нет occurrence на сегодня → **пакет одним сообщением** →
  отправка → запись occurrences. Анти-дубль через occurrences (durable).
- **Тёплый текст пакета:** `compose_reminder_message(reminders)` — лёгкий `call_llm`
  (`task_type='reminder'`, редактируемый промпт `client/reminder_message`) лепит одно
  тёплое «Напоминания …»; фолбэк — детерминированный шаблон-список.
- **API:** `POST/GET/PATCH/DELETE /clients/{id}/reminders` (require_role nutritionist,
  аудит) — не прямой Supabase мимо аудита.
- **Фронт:** в блоке «Задачи и заметки» — секция «Напоминания»: список + строка создания
  (заголовок, время, регулярность once/daily/weekly, день недели при weekly, галочка
  «нужен ответ» — задел Ф2). i18n ru/en.
- **Тесты:** матчинг recurrence×tz, пакетирование, дедуп по occurrence, фолбэк текста,
  роли эндпоинтов.

## Фаза 2 — контроль ответа + контролируемые показатели

Пункт 4 + модель показателей.

- Расширить `reminder_occurrences`: `status(sent|answered|expired|closed),
  response_event_id, followups_sent, next_followup_at`.
- Поле `reminders.expected_response` (ключ показателя | text | none) + переопределения
  профиля кадэнса.
- Профили кадэнса в `system_settings.reminder_cadence` (правятся без кода).
- Миграция каталога `client_profiles.controlled_metrics` (JSONB) + таблица `client_metrics`.
- Обобщённый инструмент `log_measurement(metric_key, value)` в intake/оркестраторе
  (kinds `measurement`, `sleep`) + категорийный роутинг хранилища.
- Планировщик: пасс детекта ответа (событие нужного типа после `sent_at` → `answered`);
  пасс догона (`now >= next_followup_at`, `< макс`, `< срок_сдаться` → повтор);
  пасс «сдались» (`>= срок_сдаться`, нет ответа → `expired` + low-severity алерт).
- Редактор напоминаний: выбор ожидаемого показателя из каталога + добавление нового
  контролируемого показателя клиента (динамические поля).
- Сон как категория `sleep` (bedtime/wake/duration, переход через полночь) + связь с
  нормой в `wellness_plans`.

## Зависимости и заметки

- Точный детект ответа (Ф2) надёжен на **оркестраторе** (сейчас — Екатерина). Для клиентов
  на старом графе — слабее; строим на оркестраторе (магистраль Ф3).
- `measurements` уже содержит `weight/neck/waist/hips` — физические замеры не требуют новой
  таблицы, только путь записи из диалога (`log_measurement`).
- Клиенту в кабинете задачи/напоминания **не показываем** — это инструмент нутрициолога.

# Переработка v2 — «Контрольный список» + шаблон сообщения (Слайс 2)

Согласовано с владельцем 3 июля 2026 (после Слайса 1 — чистки вёрстки). Цель: свести
напоминания и контролируемые показатели в ОДНУ сущность и собирать одно тёплое сообщение
по гибкому шаблону из структурированных данных.

## Идея (словами владельца)
Напоминание и контролируемый показатель — одно и то же: мы контролируем, чтобы клиент
прислал ответ на то, о чём написали в сообщении. Нутрициолог вызывает набор показателей,
отмечает, о чём напоминать/что контролировать; каждый пункт получает настройки сообщения
(время, регулярность, ждать ли ответ, повтор через, число повторов); можно добавить
произвольную строку. Из активных пунктов собирается ОДНО сообщение по шаблону.

## Ключевые решения (ответы владельца)
1. **Шаблон — гибкий через промпт**, не жёсткие плейсхолдеры. Нутрициолог правит
   промпт-шаблон (тон/структура), LLM подставляет структурированные данные. [ок]
2. **Follow-up вплетается в следующее плановое сообщение** («вчера не прислали воду»),
   а не (только) отдельным пингом через N часов. [включить]
3. **Расширить пресеты** контролируемых пунктов: + вода, приёмы пищи (завтрак/обед/ужин),
   грудь. [добавить, посмотрим]
4. **Все настройки в строке пункта**: время, регулярность, ждать ответ, повтор через,
   число повторов. **Регулярность** = ежедневно / день недели / конкретная дата (уже есть:
   recurrence daily|weekly+weekday|once+remind_date). [все указанные]

## Модель (переиспользуем существующее)
**Контрольный элемент = напоминание** (`reminders` уже несёт title/remind_at/recurrence/
weekday/remind_date/requires_response/expected_response). Каталог `controlled_metrics`
(client_profiles) остаётся «утверждённым набором» для выбора. Добавляем per-элемент
переопределение кадэнса.

### Backend
- Миграция `016`: `reminders.followup_after_hours INT NULL`, `reminders.max_followups INT NULL`
  (переопределяют профиль; NULL → профиль из `system_settings.reminder_cadence`).
  (Опц.: `measurements.chest` — если «грудь» хотим как физический столбец, а не custom.)
- Детект по типу — добавить маршруты: **вода** → событие `water_logged`; **приёмы пищи** →
  `calories_logged` (обобщить `has_event_since(client_id, event_type, since)`). Ключи
  `expected_response`: `water`, `meals`.
- Запрос «неотвеченное»: открытые/просроченные срабатывания без ответа за последние N дней
  по клиенту (для вплетения в следующий пакет).
- Сборка сообщения (`compose_reminder_message` → расширить в «структурный бриф»):
  - рекомендации из активного плана/ЗОЖ (напр. «стакан воды утром», «горькая зелень»);
  - сегодняшние запросы данных (пункты requires_response, наступившие сейчас);
  - **неотвеченное** (вчерашние/старые незакрытые) — вплести «напомни»;
  - разовые просьбы (once на сегодня, напр. замеры).
  → передать в LLM с редактируемым промптом `client/reminder_message` (шаблон).
- **Follow-up (переосмыслен):** «повтор» = повторное ВПЛЕТЕНИЕ пункта в последующие плановые
  пакеты, с интервалом ≥ `followup_after_hours` и лимитом `max_followups`; отдельный
  внутридневной пинг убираем (во избежание задвоения). Просрочка (`give_up_hours`/лимит) →
  `expired` + low-severity алерт (как в 2B).

### Frontend
- Новый `ControlListEditor` вместо `MetricsCatalogEditor` + `ReminderEditor` (в карточке
  «Задачи и заметки», теперь во всю ширину):
  - «Добавить из набора» — чипы каталога (пресеты + custom) → добавляют строку-элемент,
    предзаполнив subject + expected_response + предложенный заголовок («Прислать вес»);
  - «+ произвольная строка» (свободный текст; expected = text/none);
  - Строка: заголовок, время, регулярность (ежедневно / день недели / дата), «ждать ответ»,
    «повтор через (ч)», «число повторов»; сохранение/удаление per-строка (через reminders API);
  - Управление каталогом (добавить custom-показатель в утверждённый набор) — рядом.
- Пресеты расширяются: вес, талия, шея, бёдра, грудь, сон, вода, завтрак/обед/ужин.
