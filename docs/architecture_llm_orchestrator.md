# Архитектура: LLM-оркестратор вместо графа рёбер (ветка клиента)

> Статус: **проектирование** (1 июля 2026). Кода ещё нет. Документ — план перехода.
> Решение по модели оркестратора: **Claude Sonnet** (допущение, ожидает подтверждения владельца).

## 1. Проблема (зачем меняем)

Сейчас ход клиента обрабатывает **жёстко зашитый LangGraph**:

```
ingest → determine → load_context → dispatch → format_response → save_to_db
```

За один ход выполняется **цепочка последовательных LLM-вызовов**:

```
determine (LLM) → extract (LLM) → present/clarify (LLM) → summary (LLM)
```

Каждое звено — самостоятельная точка отказа. При надёжности звена ~90% цепочка из 4
даёт `0.9⁴ ≈ 66%`. Детерминированные рёбра **умножают** вероятность ошибки и
рассинхронизируют шаги: определитель ошибся веткой → грузим не тот контекст →
обработчик падает → `clarify`, противоречащий уже данному ответу (кейс «веганская
лазанья», PR #44).

Вдобавок роль определителя/clarify исполняет **слабая для маршрутизации модель** —
`task_type='dialog'` = Groq `llama-3.3-70b`.

## 2. Корневая идея (изначальная философия проекта)

**Сам LLM-оркестратор** понимает: что пришло → к какой теме относится → какими
инструментами воспользоваться → сколько контекста подгрузить. Граф из рёбер отнимает
у модели эту работу и множит ошибку. Возвращаем её модели.

## 3. Целевая архитектура

Один узел-агент на модели с надёжным **tool-calling**. Получает ход (текст /
`image_kind` / транскрипт голоса) + лёгкий базовый контекст. В рамках **одного
reasoning-цикла** сам вызывает инструменты.

**Ничего не выбрасываем — листовые функции графа становятся инструментами:**

| Сейчас (узел/функция)        | Инструмент оркестратора                         |
|------------------------------|-------------------------------------------------|
| `intake_store.persist_record`| `log_meal / log_water / log_weight / log_wellbeing / log_labs` |
| `intake_present.present`     | внутренний рендер ответа                         |
| `dialog_agent`               | `answer_about_client` (profile)                  |
| `nutrition_agent` (RAG)      | `give_advice` (RAG)                              |
| `load_context_node`          | `load_context(scope)` — по требованию            |
| `clarify`                    | `ask_clarifying_question`                         |

`intake_schema` (IntakeRecord), персист в БД, промпты — **без изменений**.

### Детерминированную безопасность НЕ отдаём модели
`business_rules` (`medical_rules` алерты, `access_rules` доступ/оплата) остаются
детерминированным слоем **до и после** оркестратора. LLM ведёт диалог и запись;
пороги и алерты — код. Это снижает риск, а не повышает.

## 4. Параллельные индивидуальные диалоги по `id`

Закладываем в фундамент:

1. **Состояние только по `client_id`** — никакого модульного/глобального mutable
   между пользователями.
2. **Изоляция сессии:** реестр `dict[client_id → session]` с **per-key блокировкой**.
   Разные пользователи — параллельно; два быстрых сообщения одного — сериализуются
   (состыковать с turn-буфером/debounce).
3. **Async вместо sync `graph.invoke`** — честный параллелизм под нагрузкой
   (Telegram webhook + FastAPI это позволяют); пул на I/O (LLM/БД).
4. **Память по id** — история(10) + `conversation_summary` уже per-client; станет
   инструментом `load_context`.

## 5. План миграции (strangler pattern, без большого переписывания)

### Фаза 0 — фундамент tool-calling в `utils/llm.py`
- `call_llm` сейчас текст-в-текст; `tools` = только серверный `web_search` (Claude).
- Добавить поддержку **клиентских инструментов** и цикла `tool_use → tool_result`
  (нативно у Claude; адаптеры для Gemini/OpenAI-совместимых — позже).
- Не ломать текущий контракт `call_llm` (обратная совместимость, 248 тестов зелёные).
- Тесты на новый путь отдельно.

### Фаза 1 — новый оркестратор рядом со старым
- `agents/client/agent_orchestrator.py` за **фиче-флагом** (env).
- Прод-граф остаётся как fallback.
- Инструменты-обёртки над существующими функциями + их JSON-схемы.

### Фаза 2 — обкатка на одном клиенте
- Флаг включён только для тестового `client_id` (Екатерина Юрова).
- E2E все 10 кейсов из `РАБОЧИЙ.md`; остальные клиенты — на старом графе.

### Фаза 3 — параллелизм, async, чистка
- Async-путь + per-`client_id` изоляция.
- Снять флаг, удалить мёртвые узлы графа.

## 6. Риски и границы
- Риск: качество tool-calling у слабых моделей → оркестратор на Claude, слабые — в резерв.
- Границы: безопасность/алерты не отдаём LLM; изменения `call_llm` обратно совместимы.
- Откат: фиче-флаг → мгновенный возврат на граф.
